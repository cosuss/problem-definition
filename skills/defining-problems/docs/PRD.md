# PRD — defining-problems 스킬

작성일 2026-10-13 · 대상: Claude Code / Codex 공용 Agent Skill

## 1. 배경

AI는 답을 빠르게 만들지만 잘못 정의된 문제의 답도 똑같이 빠르게 만든다(장대익, 「문제의 탄생」 p.5).
창업 수업 과제, 사업계획, 팀 운영 고민처럼 "무엇이 문제인지"부터 정해야 하는 일에서 에이전트가
사용자의 첫 프레임을 그대로 받아 그럴듯한 문서를 만들어 주면, 사용자는 문제를 이해하기 전에
결과물을 손에 쥐게 된다.

이 스킬은 사용자가 가진 로컬 자료 10종(맥킨지·산업인력공단·세쿼이아 Arc·Rittel&Webber·Meadows·
Forrester·Sarasvathy·Delmar&Shane·「문제의 탄생」·「AI와 문제정의」)의 관점을 한 절차로 묶어,
막연한 상황 설명에서 근거가 표시된 문제 정의를 뽑아낸다.

## 2. 스킬 없이 관찰된 실패 (기준선, 2026-10-13)

같은 모델에 스킬 없이 두 상황을 주고 답을 기록했다.

| 시나리오 | 잘한 것 | 실패 |
|---|---|---|
| A. 농가용 AI 병해충 진단 앱, 내일 마감, "질문하지 말고 써줘" | 수치 자리를 대괄호로 비움, 끝에 "(가설) 표시하라" 권고 | ① 문제를 "밭에서 바로 쓸 진단 수단이 없다"(=내 앱의 부재)로 정의하고 '해결 방향' 절까지 포함 ② '진단이 병목'이라는 사용자 전제를 의심하지 않음, 대안 프레임 0개 ③ 농민의 대응 순서·원인을 근거 없이 단정문으로 서술 |
| B. 동아리: 회의 길고 신입 이탈, 벌금·회식 대책 뒤 악화 | 가설임을 밝힘, 확인 방법 3개 제시, 대책이 비용만 올렸다는 구조적 설명 | ① 프레임 1개만 제시(대안은 끝에 한 줄) ② 누구의 문제인지·경계 미설정 ③ 문제 성격 진단 없음 ④ 답마다 형식이 달라 재사용 불가 |

모델은 이미 가설 표시와 확인 질문을 어느 정도 한다. 스킬은 그 부분을 반복해 가르치지 않고
위 실패만 겨냥한다.

## 3. 사용자와 사용 상황

- 1차 사용자: 학생 창업가(AI학과 2학년). 창업 수업 문제정의 과제, 사업 아이템 검증, 팀·동아리 운영 문제.
- 사용 상황
  1. 아이디어·해결책은 있는데 누구의 어떤 문제인지 흐릿하다.
  2. 문제 정의문(problem statement)을 써서 제출해야 한다.
  3. 대책을 써도 같은 문제가 되풀이된다.
  4. 이미 쓴 문제 정의문을 검토받고 싶다.
  5. 고객·현장 인터뷰 기록이 있고, 거기서 문제 후보를 뽑아 견주고 싶다. (2026-10-14 추가)

## 4. 목표

| ID | 목표 | 판정 방법 |
|---|---|---|
| G1 | 문제 정의문에 해결책·제품명이 들어가지 않는다 | 산출물의 문제 정의문에 "~가 없다/부족하다" 또는 제품·기능 명사가 없음 |
| G2 | 근거 없는 서술이 사실처럼 읽히지 않는다 | 모든 서술에 [확인]/[진술]/[가정] 등급이 붙음 |
| G3 | 채택한 프레임 외에 경쟁 프레임이 2개 이상 기록된다 | 프레임 표에 3행 이상, 행마다 전제하는 해결 방향이 다름 |
| G4 | 문제 성격에 맞는 정의 방식을 쓴다 | 성격 진단 결과와 그에 따른 처리(반증 조건, 손실 한도, 이해관계자별 판정 등)가 산출물에 있음 |
| G5 | 시간 압박이 있어도 사용자를 붙잡지 않는다 | "질문하지 마" 조건에서 질문 0개로 초안이 나오고 가정이 표시됨 |
| G6 | 산출물 형식이 고정되어 다시 쓸 수 있다 | 템플릿의 절 구성이 실행마다 같음 |

## 5. 비목표

- 해결책 설계, 기능 기획, 사업계획서 전체 작성. 문제 정의가 끝나면 다른 스킬·작업으로 넘긴다.
- 시장 규모 추정, 경쟁사 조사 대행. 필요한 사실 확인은 하지만 조사 보고서를 만들지 않는다.
- 정답 판정. wicked 문제에는 확정적 정식화가 없으므로(Rittel&Webber p.161) "채택한 정의 하나"를 낸다.
- 원전 요약·개념 강의. 참고 파일은 실행 규칙과 판별 질문만 담는다.

## 6. 요구사항

### 기능

| ID | 요구사항 | 근거 자료 |
|---|---|---|
| F1 | 진입 모드 3가지: 초안(묻지 않고 작성) / 대화(한 번에 한 질문) / 검토(기존 정의문 판정) | 기준선 A, PM-Skills 진행 규약 |
| F2 | 현상을 관찰 가능한 사실로 고정: 누가·언제·어디서·빈도·현재의 우회 행동 | 「문제의 탄생」 p.12, p.57 |
| F3 | 해결책 분리: 문제 문장에서 해결책을 빼고 `보류한 해결책` 칸으로 옮김 | Meadows p.171, 「문제의 탄생」 p.51 |

| F6 | 반복되거나 대책이 실패한 문제는 사건→패턴→구조로 내려가고 시스템 함정과 대조 | Meadows 5장, Forrester pp.9–10 |
| F7 | 프레임 3개 이상 생성, 프레임별 전제 해결 방향 표기 후 선택 | Rittel 속성 9, 「문제의 탄생」 p.50 |
| F8 | 한 문장 문제 정의문: [누가][어떤 상황]에서 [무엇을 하려 할 때] [어떤 장애] 때문에 [어떤 비용]을 치른다 | 「문제의 탄생」 p.62, 「AI와 문제정의」 p.7 |
| F9 | 품질 판정: 좋은 문제 7조건, 가짜 문제 3징후, 너무 큰/작은 문제 | 「문제의 탄생」 p.54–61 |
| F10 | 가장 위험한 가정 3개와 가장 싼 확인 방법, 반증 조건 | Delmar&Shane p.1167, Meadows p.172 |
| F12 | 후보 모드: 인터뷰 발언을 한 것·내놓은 것·평가·의향으로 나누고, 후보 3~5개를 반대 증거·대체재와 함께 견주어 검증 순서를 낸다 | 진형석 특강(2026-10-12), 「문제의 탄생」 p.54 |
| F11 | 고정 산출물 템플릿(표 중심, 설명은 절마다 세 줄 이하) | 기준선 B |

### 비기능

- 본문(SKILL.md)은 150줄 이내. 대화 내내 컨텍스트에 남고 자동 압축 뒤에는 앞부분만 다시 붙기 때문이다.
- 참고 파일은 한 단계 깊이로만 두고 조건에 맞을 때만 읽는다.
- Claude Code와 Codex에서 같은 파일로 동작한다(공통 frontmatter만 필수로 사용).
- 한국어로 진행한다. 원전의 용어는 원어를 병기한다.

## 7. 성공 지표

- 품질: 기준선 시나리오 A·B를 스킬 적용 상태로 다시 돌렸을 때 G1~G6을 모두 충족.
- 트리거: `evals/trigger-evals.json`의 should-trigger 질의에서 스킬이 호출되고 near-miss 질의에서는 호출되지 않음.
- 사용자 체감: 과제·사업 문서에 그대로 붙일 수 있는 한 문장 정의문이 나오고, 무엇을 확인해야 하는지 바로 알 수 있음.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 질문이 많아 사용자가 지침 | 질문 5개 안에 첫 초안, 초안 모드 제공 |
| 틀·용어를 과하게 적용해 산출물이 길어짐 | 조건에 맞는 렌즈만 적용, 템플릿 분량 제한 |
| Hard Fact 문제를 '가짜 문제'로 잘못 기각 | 체념·우회 행동을 가짜 문제 징후와 구분하는 규칙을 렌즈 파일에 명시 |
| 수단에서 출발(effectuation)과 수단에 맞춘 원인 선택(편향) 혼동 | 만들 것을 고를 때와 원인을 진단할 때를 구분하는 규칙 명시 |
| 다른 스킬(brainstorming 등)과 트리거 충돌 | description에 제외 조건 명시, near-miss 트리거 eval |
